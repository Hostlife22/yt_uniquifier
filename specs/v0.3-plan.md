# yt-uniquifier v0.3 — HDR→SDR · Parallel GPU · Distributed batch

> Roadmap follow-up к [v0.2](./v0.2-plan.md). Три независимые тяги:
> HDR-фильмы для SDR-аудитории, выжимание производительности из единого
> GPU, и горизонтальное масштабирование на парк машин.
>
> **Явно вне scope:** OCR / re-render image-based субтитров (PGS/DVB).
> Они остаются в режиме «warn + skip» как с v0.1.
> **Также вне scope:** GUI / REST API / web UI (унаследовано из v0.2 правила).

---

## Context: что v0.2 не закрывает

| Проблема | Текущее состояние | Целевое v0.3 |
|---|---|---|
| HDR-фильм для SDR-канала | preflight `fail` без `keep_hdr=true`; нет тонемап-пути | один прогон с осмысленным маппингом в SDR |
| GPU-encoding workers | hardcoded sequential (один VRAM-контекст) | до 3-5 параллельных NVENC-сессий на consumer-картах |
| Обработка фильмотеки на парк машин | sequential `batch` на одной машине | leasing-очередь на shared FS / S3 |

Два из трёх (HDR→SDR, parallel GPU) — относительно локальные расширения
существующего pipeline. Distributed batch — отдельный слой, требующий
координации.

---

## Архитектурные принципы v0.3

1. **Контракты v0.2 неизменны.** `Plan`/`Profile`/`SourceMeta`/`QAReport`
   расширяются полями с дефолтами, не ломаются.
2. **GPU-параллелизм через query, не через предположения.** Лимит
   воркеров определяется через `nvidia-smi --query-gpu=memory.free`
   (или эквивалент по вендору), не задаётся пользователем вслепую.
3. **Distributed lock — на самом простом примитиве:** atomic rename
   в shared dir. Никаких redis/sqlite зависимостей в v0.3.
4. **Все три фазы независимы.** Можно делать в любом порядке.

## Phase 11 — HDR → SDR tonemap (1.5 дня)

**Goal:** один прогон конвертирует HDR-источник (PQ/HLG) в SDR-выход с
осмысленным маппингом яркости (не клиппинг highlights). Качество vs HDR
original измеримо в QA через тонемап-aware VMAF.

**Scope:**

**In:**
- Новый transform `video.tonemap_sdr` с параметром `algorithm`
  (`hable | reinhard | mobius | aces`).
- `core/transforms/hdr_wrap.py` дорабатывается: помимо обёртки в PQ-домене
  даёт `to_sdr_chain()` для tonemap-конвертации.
- `core/pipeline.py`: если в plan включён `video.tonemap_sdr`, источник HDR
  пропускается через linear-tonemap-bt709-yuv420p блок перед цветовыми
  трансформами.
- `core/preflight.py`: при `video.tonemap_sdr` снимает требования
  `keep_hdr=true` и 10-bit encoder — выход SDR.
- `profiles/cid_aware_hdr_to_sdr.yaml` — рекомендуемый рецепт.
- QA: добавить флаг `vmaf_hdr_aware: bool` в `vmaf.compute()` —
  `libvmaf=phone_model=0:hdr10` для корректной оценки HDR↔SDR.

**Not in:** Dolby Vision (нужен detect profile 5/7/8 — отложено),
HDR10+ dynamic metadata, multi-target output одного прогона.

**Modules:**

`core/transforms/video_tonemap.py` (новый):
```python
class TonemapSDRParams(BaseModel):
    algorithm: Literal["hable", "reinhard", "mobius", "aces"] = "hable"
    peak: float = Field(default=1000.0, ge=100.0, le=10000.0)
    desat: float = Field(default=0.0, ge=0.0, le=1.0)

# Filter chain:
#   zscale=t=linear:npl=<peak>,
#   tonemap=<algorithm>:desat=<desat>:peak=<peak/100>,
#   zscale=t=bt709:m=bt709:p=bt709:r=tv,
#   format=yuv420p
```

`core/pipeline.py`:
- `_target_pix_fmt()`: если в transforms есть `video.tonemap_sdr` → всегда
  `yuv420p` (SDR), независимо от `keep_hdr`.
- HDR-grouping (Phase 6) скипается, если применяется tonemap — вместо
  zscale-roundtrip раз и навсегда переходим в SDR.

`core/preflight.py`:
- Новый код `hdr.tonemap.ok` (severity=ok) когда HDR + tonemap.
- Подавляет `hdr.color.transforms` fail когда tonemap присутствует.

`profiles/cid_aware_hdr_to_sdr.yaml`:
```yaml
name: cid_aware_hdr_to_sdr
description: HDR source → SDR output with CID-divergence transforms.
transforms:
  - id: video.tonemap_sdr        # first — flatten HDR into SDR
    params: {algorithm: hable, peak: 1000}
  - id: video.crop_resize
    params: {max_strength: 0.04}
  - id: video.color_eq
    params: {brightness: 0.015, contrast: 1.022, gamma: 0.99, saturation: 1.04}
  # … rest matches cid_aware
keep_hdr: false
target_codec: h264
seed_strategy: per_run
```

**Acceptance:**

```bash
# HDR source through cid_aware_hdr_to_sdr → SDR mp4.
yt-uniq run hdr_master.mkv \
  --profile profiles/cid_aware_hdr_to_sdr.yaml \
  --out hdr_as_sdr.mp4 --encoder libx264
yt-uniq probe hdr_as_sdr.mp4 | jq '.video[0].color'
# {"is_hdr": false, "transfer": "bt709", ...}

# Preflight no longer fails on HDR + color transforms when tonemap is present.
yt-uniq preflight hdr_master.mkv --profile profiles/cid_aware_hdr_to_sdr.yaml
# exit 0
```

**Tests:**
- `tests/unit/test_transform_tonemap.py` — algorithm enum, filter snapshot per algorithm.
- `tests/unit/test_pipeline_tonemap_path.py` — pipeline emits the tonemap chain instead of HDR-keep wrap.
- `tests/unit/test_preflight_tonemap.py` — HDR + tonemap → no `hdr.color.transforms` fail.
- `tests/integration/test_hdr_to_sdr_roundtrip.py` — synthetic PQ clip → run → output is BT.709, VMAF tonemap-aware ≥ 75 (lower bar because tonemapping is lossy by design).

**Risks:**
| Риск | Митигация |
|---|---|
| `hable` пережимает highlights | дать `--tonemap-algorithm` опцию профиля; документация: aces — лучше для cinema content |
| VMAF на HDR↔SDR пара даёт меньше чем VMAF HDR↔HDR | другой target (≥75 вместо ≥88); явный note в QA report |
| Tonemap+color_eq компонуется некорректно | tonemap должен идти ПЕРВЫМ в transforms list; pipeline валидирует порядок |

## Phase 12 — Parallel GPU encoding (2 дня)

**Goal:** на NVIDIA consumer-картах (RTX 3060+) запускать 2-3 параллельных
NVENC-сессии (per-driver лимит). На VideoToolbox/QSV — 2-4. Не делать
больше воркеров чем VRAM/драйвер выдержит.

**Scope:**

**In:**
- `core/encoder.py`: `EncoderCandidate.max_parallel: int` (через
  query VRAM / driver limit per vendor).
- `core/segmenter.parallel_safe(plan)` теперь возвращает `int` (max workers
  для этого encoder'а), не `bool`.
- `core/segmenter.process_video_segments_parallel`: использует
  `min(workers_requested, plan.encoder.max_parallel)`.
- Runner: ловит NVENC `OpenEncodeSessionEx failed: out of memory` (return
  code 24) → retry с back-off + меньшим параллелизмом.
- Документация: для NVENC consumer-чипов unpatched драйверов лимит = 3
  сессии; passing `--workers 5` молча даунгрейдится.

**Not in:** разбиение одного сегмента между GPU и CPU; multi-GPU dispatch
(`CUDA_VISIBLE_DEVICES` round-robin — v0.4).

**Modules:**

`core/encoder.py`:
```python
class EncoderCandidate(BaseModel):
    name: str
    vendor: EncoderVendor
    codec: EncoderKind
    works: bool
    error: str | None = None
    max_parallel: int = 1   # NEW: how many concurrent sessions are safe

def _detect_max_parallel(vendor: EncoderVendor) -> int:
    """Query driver/hardware for the safe concurrent session count.

    - nvenc: parse `nvidia-smi --query-gpu=memory.free` and divide by
      ~500 MB per 1080p session; cap at 3 for consumer chips, 8 for
      pro/Quadro (detect via product_name).
    - qsv:   2 (most Intel chips support multi-session)
    - videotoolbox: 2 (M-series can do more but Apple doesn't expose limit)
    - amf:   2
    - x264 / x265: cpu_count() // 2
    """
```

`core/segmenter.py`:
```python
def parallel_safe(plan: Plan) -> int:
    return plan.encoder.max_parallel
```

`process_video_segments_parallel`:
```python
effective_workers = min(workers, parallel_safe(plan))
```

`core/runner.py`:
- Catch return code 24 + stderr regex `OpenEncodeSessionEx failed`:
  → sleep 2s, retry once with `force_workers=1`. If still fails — propagate.

**Acceptance:**

```bash
# On a machine with NVENC:
yt-uniq probe --encoders | jq '.[] | select(.name=="h264_nvenc")'
# {"name":"h264_nvenc","vendor":"nvenc","works":true,"max_parallel":3,...}

# Run with workers=8 on h264_nvenc — orchestrator downgrades to 3.
yt-uniq run movie.mp4 --profile cid_aware.yaml --out out.mp4 \
  --encoder h264_nvenc --workers 8
# Log shows: "workers downgraded 8 → 3 (h264_nvenc consumer limit)"
# Wall time ~ 1/3 × single-NVENC baseline.
```

**Tests:**
- `tests/unit/test_encoder_max_parallel.py` — mocked nvidia-smi output → expected `max_parallel`; pro card → 8; missing tool → 1.
- `tests/unit/test_parallel_segments_cap.py` — workers=8 with max_parallel=3 → ThreadPool created with 3.
- `tests/unit/test_runner_nvenc_oom_retry.py` — mock Popen returning code 24 + "OpenEncodeSessionEx" → second call with workers=1 succeeds.
- `tests/integration/test_real_parallel_nvenc.py` — `@pytest.mark.skipif(no nvenc)` — workers=4 → segments encoded concurrently (timestamps overlap).

**Risks:**
| Риск | Митигация |
|---|---|
| consumer драйвер unpatched: лимит 3, не 8 (NVIDIA NVENC restriction) | дефолт max_parallel=3 для consumer; патч-инструкция в docs (нелегально для коммерческой раздачи, упомянуть) |
| nvidia-smi не установлен (Linux Docker без NVIDIA tools) | fallback max_parallel=2 + warn |
| Apple M-series VideoToolbox имеет внутреннюю serialization | определяем эмпирически: запускаем 2 параллельных testsrc encodes, если time ≈ 2× sequential — даунгрейдим max_parallel=1 |
| AMF (Windows) только частично работает в Linux | работа в детект через nullsrc остаётся; если работает — max_parallel=2 |

## Phase 13 — Distributed batch (shared-FS leasing) (2.5 дня)

**Goal:** N машин с общей файловой системой (NFS / SMB / shared S3 with
fsspec) обрабатывают одну очередь файлов без координатора. Лизинг через
atomic rename. Никаких redis/database зависимостей.

**Scope:**

**In:**
- `core/queue/leasing.py` — abstraction над shared-FS lease (atomic
  `mv pending/<file> in_progress/<host>/<file>` → process → mv to `done/`).
- `cli/cmd_queue.py` — `yt-uniq queue add/list/status/reset`.
- `cli/cmd_worker.py` — `yt-uniq worker --queue <dir> --profile X.yaml
  --out <dir>` — long-running, picks the next leasable file, processes,
  moves to `done/`, repeats.
- Lease state-of-the-art: heartbeat file `<host>.alive` updated every
  30s; stale lease (no heartbeat > 5min) → reaper relocks to another host.
- Backed by any POSIX FS that supports atomic rename across directories
  on the same filesystem (NFSv4, ext4, APFS, ZFS).

**Not in:** S3 object lock (отдельный backend, отложено в v0.4); web
dashboard for queue state; multi-encoder-vendor coordination (each worker
uses what it has).

**Modules:**

`core/queue/leasing.py`:
```python
@dataclass
class QueueLayout:
    root: Path           # shared directory
    pending: Path        # root/pending/
    in_progress: Path    # root/in_progress/<host>/
    done: Path           # root/done/
    failed: Path         # root/failed/

class FileQueue:
    def __init__(self, root: Path) -> None: ...
    def add(self, path: Path) -> None:
        """Copy/move file into pending/."""
    def lease(self, *, host: str, lease_sec: int = 300) -> Path | None:
        """Atomically rename a pending file into in_progress/<host>/.
        Returns the new path or None if queue empty."""
    def release_done(self, leased_path: Path) -> None: ...
    def release_failed(self, leased_path: Path, error: str) -> None: ...
    def heartbeat(self, host: str) -> None:
        """Touch <host>.alive in in_progress/<host>/."""
    def reap_stale(self, *, stale_sec: int = 300) -> int:
        """Find in_progress/* dirs without recent heartbeat, move their
        files back to pending/. Returns count."""
    def stats(self) -> dict[str, int]:
        """Counts of pending / in_progress / done / failed."""
```

`cli/cmd_queue.py` (typer sub-app):
```
yt-uniq queue init <dir>           # set up the directory structure
yt-uniq queue add <queue_dir> file1.mp4 file2.mp4 ...
yt-uniq queue status <queue_dir>
yt-uniq queue reset <queue_dir> [--include-failed]
```

`cli/cmd_worker.py`:
```
yt-uniq worker <queue_dir> \
  --profile profiles/cid_aware.yaml \
  --out-dir /shared/uniq/ \
  --encoder libx264 \
  --workers 4 \
  --stop-after-empty
```

Loop:
1. Heartbeat self.
2. Lease one file. If empty + `--stop-after-empty` → exit.
3. `orchestrator.run_full(plan, options)`.
4. On success: move to `done/`; on exception: move to `failed/<host>/<file>.err.txt`.
5. Periodically (every N files) reap_stale.

**Acceptance:**

```bash
# On machine A (NFS server, queue root /shared/queue):
yt-uniq queue init /shared/queue
yt-uniq queue add /shared/queue ~/movies/*.mp4
yt-uniq queue status /shared/queue
# pending: 12, in_progress: 0, done: 0, failed: 0

# On machine A:
yt-uniq worker /shared/queue \
  --profile /shared/profiles/cid_aware.yaml \
  --out-dir /shared/uniq/ --workers 4 &

# On machine B (mounts /shared via NFS):
yt-uniq worker /shared/queue \
  --profile /shared/profiles/cid_aware.yaml \
  --out-dir /shared/uniq/ --workers 4 &

# A and B both pick different files; queue drains without double-processing.
yt-uniq queue status /shared/queue   # observable on either machine
```

**Tests:**
- `tests/unit/test_queue_layout.py` — `init` creates pending/in_progress/done/failed.
- `tests/unit/test_lease_atomic.py` — two threads call `lease()`; each gets a different file (no double-lease).
- `tests/unit/test_lease_empty.py` — empty queue → lease returns None.
- `tests/unit/test_heartbeat_reaper.py` — stale lease > stale_sec → reap_stale returns 1 and file is back in pending.
- `tests/integration/test_worker_drains_queue.py` — local-only emulation: 2 workers in subprocess, 6 tiny clips, drain to done, no duplicates.

**Risks:**
| Риск | Митигация |
|---|---|
| NFS rename не атомарен через client cache | требуем `noac` mount option в docs; backup: lock-file check after rename |
| Worker умер во время encoding | heartbeat файл протух → reaper переоффлоадит. Уже сделанные сегменты в work_dir теряются (work_dir per-worker per-input) |
| Два worker'а на одной машине с одним --out-dir конфликтуют по концат-temp | каждый worker создаёт `out_dir/<host>/<pid>/` под temp + atomic move в финальный путь |
| Worker не имеет такого же encoder как тот, что в очереди по-разному | в lease нет привязки к encoder; каждый worker сам решает через `pick_encoder(prefer=[…])` и пишет свой выход. Acceptable: разные машины — разные encoder'ы, разные fingerprint'ы variant'ов |
| Shared FS не поддерживает atomic rename across dirs | preflight `yt-uniq queue init` делает rename-test и failит с понятным сообщением |
| Очередь распухает без cleanup | `yt-uniq queue reset --done-older-than 30d` (v0.3.1) |
