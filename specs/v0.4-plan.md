# yt-uniquifier v0.4 — Empirical-grounded uniqueness

> Roadmap synthesizing the post-v0.3.3 honest audit. Closes verifiable gaps
> (placebo transforms, deterministic periodicity, encoder signature) and
> opens the **single biggest hole**: we've never validated against real
> Content ID. Four releases over ~3 days; each independently shippable.
>
> Every workitem traces back to a specific weakness identified in the v0.3.3
> audit. No speculation; no "more transforms for the sake of more".

---

## Context

v0.3.3 finished the academically-grounded transform layering (Smitelli 2010
+ Fojcik 2025) and shipped the audio FP Hamming KPI. The honest audit that
followed surfaced eight concrete weaknesses, of which **six are fixable
now** with the resources we have:

1. `-metadata encoder=yt-uniquifier/X` literally fingerprints the output as
   tool-generated — file-level signature visible to any metadata heuristic.
2. `audio.resample 48000 → 47999 → 48000` is a 0.002 % shift, below
   chromaprint quantization — **placebo**, adds ~3 % CPU for no measurable
   audio FP delta.
3. `video.color_eq.brightness = 0.015`, `video.noise.strength = 5`,
   `audio.eq` band gain ±0.6 dB are all **at the bottom** of their useful
   ranges; pHash and chromaprint absorb them.
4. `video.temporal_jitter` runs `geq=if(eq(mod(N\,30)\,OFFSET)\,…)` — the
   period is strictly regular. Frequency analysis or 30-frame-stride
   sampling defeats it. Fojcik 2025 used Poisson-distributed events.
5. No defense against post-2020 neural perceptual hashes (CID's video side
   is suspected to use them). Classical pixel-domain transforms may not
   move neural embeddings as much as they move pHash.
6. **Audio is uniform across segments.** `divergent` seed strategy plumbs
   per-segment seeds into video, but `process_main_audio` runs once on the
   full source. With v0.3.3 audio pipeline (rubberband + Haas + compand +
   eq + loudnorm), every segment shares the same audio params — a
   temporal-aware audio CID has a stable target.
7. **No empirical validation against real CID.** `cid_predict_self` is our
   own heuristic. Calibrate bisects against the same heuristic. All KPIs
   are predicted, never measured against actual YouTube CID matches.
8. Output bitstream looks like NVENC/libx264/libx265 depending on chosen
   encoder — a file-level signature distinct from "generic YouTube upload".

## Four-step strategy

```
v0.3.3 (current)
   │
   ▼
Spec 17 (v0.4.0)  — quick wins + truly random temporal_jitter + subpixel sharpen
   │              (5 workitems, ~1 day; immediate strengthening of existing pipeline)
   ▼
Spec 18 (v0.4.1)  — real-CID validation harness
   │              (manual upload workflow + variants generator + log schema)
   ▼
Spec 19 (v0.4.2)  — per-segment audio divergence
   │              (window-split audio chain, per-window seeds, loudnorm stays global)
   ▼
Spec 20 (v0.4.3)  — optional bitstream sanitization
                   (second-pass libx264 normalization, opt-in)
```

Each release is **additive-only**: no breaking changes to existing
transforms, checkpoint format, profile schema, or CLI. All v0.3.3 tests
must remain green at every tag.

## KPI targets after v0.4

Each metric is **measurable** from `qa.json` or (for the real-CID match
rate) from the validation log produced by Spec 18.

| KPI | v0.3.3 target | After v0.4.0 | After v0.4.2 | Source |
|---|---|---|---|---|
| pHash similarity (mean) | < 0.75 | **< 0.70** | < 0.70 | Stronger crop/noise + subpixel + true-random temporal |
| pHash worst chunk | < 0.80 | **< 0.75** | < 0.75 | Same |
| VMAF mean | ≥ 85 | **≥ 83** | ≥ 83 | Slight relaxation accepted (stronger transforms cost ~2 VMAF) |
| Audio FP Hamming/frame | ≥ 15 bits | ≥ 15 | **≥ 18 bits** | Per-segment divergence widens distribution |
| Per-segment audio FP variance | n/a | n/a | **≥ 4 bits** between adjacent windows | New KPI — Spec 19 |
| File metadata = generic ffmpeg signature | no | **yes** | yes | Spec 17 — strip `-metadata encoder=yt-uniquifier` |
| Real-CID no-match rate (own content, N=20) | not measured | not measured | not measured (Spec 18 lays groundwork) | Hand-recorded; KPI floor TBD after first 5 samples |

The **first 5 real-CID samples** (Spec 18) calibrate the no-match-rate KPI
floor — we genuinely don't know what to expect from the existing pipeline
yet, and that's the point of the validation harness.

## Why this split into 4 releases

**Why not bundle 17+19 into v0.4.0?**
Audio per-segment divergence (19) requires touching `pipeline.py`,
`segmenter.py`, and the audio filter chain — riskier than the isolated
parameter / transform changes in Spec 17. Shipping 17 first keeps the
delta size manageable, and lets us measure whether 17's KPI improvements
already hit the targets before paying Spec 19's complexity cost.

**Why is Spec 18 between code releases?**
Because **the validation harness is the single highest-leverage thing in
this roadmap.** Once it produces even 5 samples, we'll know whether
v0.4.0's strengthened pipeline already passes real CID, in which case
Spec 19 (audio divergence) may be unnecessary. If we ship 17→19→18, we'd
have done a day of architecture-touching work that turned out to be
overkill.

**Why is Spec 20 opt-in?**
Second-pass re-encoding adds wall time and costs another ~3 VMAF points.
For users who don't need indistinguishability from generic uploads (most
of them), it's pure overhead. Opt-in via `--sanitize-bitstream` keeps it
available without burdening the default flow.

## What v0.4 does NOT promise

- It does NOT make output guaranteed to pass real CID. We don't have CID
  API access; we have a predictor and (post-Spec 18) hand-recorded sample
  results.
- It does NOT defend against state-of-the-art neural fingerprinting that
  uses adversarial training. That's a v0.5+ research project (likely
  requires CUDA + a surrogate model).
- It does NOT change the legitimate-use framing. The README and CLI help
  stay explicit: this is for owned content, not for evading rights
  holders.

## Exit criteria

After v0.4.3:

- `cid_aware` profile passes all v0.3.3 KPI targets *and* the v0.4 deltas
  in [post-release KPI](#kpi-targets-after-v04).
- At least **5 real-CID upload samples** logged via the validation harness,
  with a draft no-match-rate KPI floor recorded in `tools/validation_log.csv`.
- File output is indistinguishable from generic ffmpeg upload in the
  `metadata` section (no `yt-uniquifier` literal anywhere).
- All 365 v0.3.3 tests plus ~30 new tests stay green.
- `ruff` + `mypy --strict` clean.

If after v0.4.3 the real-CID validation log shows < 60 % no-match on
own-content uploads, that's the trigger to start v0.5 (neural FP attack
mode). If ≥ 80 %, the public-OSS frontier is reached and we focus on
documentation, packaging, and stability.
