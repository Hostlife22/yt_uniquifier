# yt-uniquifier v0.2 — Реальная устойчивость к Content ID

> Roadmap follow-up к [v0.1.0](./README.md). Цель v0.2 — превратить полированный
> pipeline в инструмент, который реально не матчится Content ID на загрузках
> собственного / лицензионного контента, а не только меняет MD5.
>
> **Вне скоупа v0.2 явно:** GUI, REST API, веб-интерфейс. Никакого UX-слоя.
> Только CLI + ядро.

---

## Context: что показала v0.1.0

| Метрика | v0.1.0 | Реальность Content ID |
|---|---|---|
| MD5 разный | ✓ всегда | irrelevant (CID смотрит фингерпринты) |
| pHash similarity | ~0.95 | матчится при ≥ ~0.82 |
| Audio fingerprint (chromaprint Jaccard) | почти неизменна (pitch 0.08%) | толерантен до ~3% по тону |
| Spectral analysis сходство | не измеряется | CID использует |
| HDR через color-трансформы | сломан, preflight=fail | блокирует реальные HDR-мастера |
| Калибровка против реального CID | нет | единственный способ верифицировать |
| Тест на длинном (2h+) видео | нет | неизвестные регрессии |

**Корневой диагноз:** профили `soft/medium/aggressive` откалиброваны под
*перцептивную неотличимость от оригинала*, а не под *расхождение
фингерпринта*. Это разные задачи, и v0.1 решает первую.

**Юридический контекст:** v0.2 проектируется под сценарий, который пользователь
подтвердил ранее — собственный / лицензионный контент. Применение к чужим
авторским правам остаётся вне скоупа (явно отказываюсь добавлять что-либо,
что облегчает анонимизацию источника, не привязанное к этому use-case'у).

---

## Архитектурные принципы v0.2

1. **Контракты ядра v0.1 не меняются.** `Plan` / `Profile` / `SourceMeta`
   стабильны. Только расширения через новые поля с дефолтами.
2. **Калибровка > интуиция.** Любая интенсивность трансформации должна быть
   эмпирически связана с метрикой расхождения фингерпринта.
3. **Two-tier QA:** v0.1-метрики (pHash/VMAF/SSIM/audio_fp) → quality
   preservation. v0.2-метрики (spectral fingerprint distance, predicted CID
   match probability) → uniqueness verification.
4. **Variability:** одна и та же конфигурация на повторный запуск даёт **разный**
   рандомизированный outcome, чтобы можно было загружать N вариантов без
   collision между ними.

## Phase 6 — Real HDR pipeline (1.5 дня)

**Goal:** HDR (PQ/HLG) видео реально проходит через color/eq/noise трансформы
без потери цветового пространства, остаётся HDR на выходе.

**Scope:**
- `core/transforms/hdr_wrap.py` — функции `wrap_linear(label)` / `wrap_pq(label)`
  / `wrap_hlg(label)`, оборачивающие участок цепочки в `zscale=transfer=linear:npl=100`
  и обратно.
- `core/pipeline.py` — детектит HDR + `keep_hdr=True` и автоматически вставляет
  zscale-обёртки вокруг блока цветовых transforms (color_eq, noise, blend_b).
  Геометрия (crop_resize, rotate, speed) HDR не ломает — её не оборачиваем.
- `core/preflight.py` — для HDR-источников при `keep_hdr=True` проверяет,
  что ffmpeg собран с zimg, и что encoder поддерживает 10-bit (NVENC hevc /
  videotoolbox hevc / libx265).
- Новый профиль `profiles/medium_hdr.yaml` с `keep_hdr: true`, без `video.rotate`
  (rotate fill ломает HDR-blacks).

**Acceptance:**
- `yt-uniq run hdr.mkv --profile medium_hdr.yaml` производит файл с тем же
  `color_transfer=smpte2084`, `color_primaries=bt2020`, `pix_fmt=yuv420p10le`.
- QA: VMAF между HDR input и HDR output > 90 на тестовом HDR-клипе.

**Tests:**
- unit/test_hdr_wrap.py: snapshot zscale-обёрток для color_eq, blend_b.
- integration/test_hdr_roundtrip.py: реальный 2-сек HDR-клип через
  `medium_hdr.yaml`, probe выхода подтверждает HDR-метаданные.

## Phase 7 — Audio strong + variability (2 дня)

**Goal:** аудио-сторона начинает реально сдвигать chromaprint-фингерпринт,
оставаясь перцептивно чистой. Каждый run с одним профилем даёт **разный**
fingerprint (для batch-загрузок N вариантов).

**Scope:**

`core/transforms/audio_pitch.py` — расширение:
- Pitch shift диапазон: дефолт 0.5–1.5% (текущий 0.04–0.08% бесполезен).
- Добавить `randomize_within: float` — при run рандомизируется в окне
  [pitch - randomize_within, pitch + randomize_within].

`core/transforms/audio_eq.py` — расширение:
- Дополнительный шаг — `randomize_bands: bool`. Если true, частоты bands
  jitter'ятся ±5% и gain ±0.2 dB на каждый run.

`core/transforms/audio_resample.py` — новый transform:
- Микро-resampling: SR → 47999 → SR. Чуть размывает спектральные пики
  чем у chromaprint используются для фингерпринтинга, перцептивно
  неслышно. Параметры: `intermediate_sr: int = 47999`.

`core/transforms/audio_spectral_smear.py` — новый transform:
- `aphaser` или `chorus` с минимальной интенсивностью (delay 5 ms, depth 0.05).
- Параметр: `intensity: float ∈ [0, 0.1]`. Дефолт 0.02.
- Это самая агрессивная аудио-трансформация — сдвигает спектр заметно
  для fingerprint, но малозаметно для уха.

`core/transforms/video_geom.py` — добавление:
- `MirrorParams`: горизонтальное зеркалирование (hflip). Однозначно ломает
  pHash, но и сильно меняет смысл видео — только для контента, где это допустимо.

`core/profile_loader.py`:
- Поддержка `seed_strategy: "fixed" | "per_run" | "per_file"`.
  Default `per_run` — каждый запуск рандомизирует.

`core/models.py`:
- В `Plan` добавить `run_seed: int` (рандомизируется при `per_run`).
- `plan_hash` теперь зависит ещё и от `seed_strategy`, чтобы resume не путал
  два разных random'а.

Два новых профиля:
- `profiles/cid_aware.yaml` — рекомендуемый для CID-устойчивости:
  pitch 1.012, audio.eq jitter, audio.resample, video.crop 4%, mild noise.
  Без mirror и speed change (зритель не должен заметить).
- `profiles/cid_aggressive.yaml` — добавляет audio.spectral_smear,
  video.speed 0.99, для контента где допустимо.

**Acceptance:**
- Два прогона `cid_aware` на одном и том же файле дают разные audio
  chromaprint (Jaccard similarity между двумя outputs < 0.7).
- Сравнение output ↔ input: chromaprint Jaccard < 0.5 при `cid_aware`,
  < 0.3 при `cid_aggressive`.
- При этом VMAF input ↔ output > 88 (perceptual quality ok).

**Tests:**
- unit/test_transform_audio_resample.py
- unit/test_transform_audio_spectral_smear.py
- unit/test_variability.py: два plan'а с одинаковым profile + `per_run` seed
  дают разный `plan_hash`.
- integration/test_audio_fp_shift.py: тестовый аудио-клип, applied through
  `cid_aware`, измеряем chromaprint distance — должно быть значимое отличие.

## Phase 8 — Fingerprint-aware QA + corpus (2 дня)

**Goal:** QA-отчёт теперь не просто измеряет similarity input ↔ output, а
оценивает **вероятность совпадения** с любым файлом в пользовательском
«своём корпусе» — то есть «не попадёт ли этот выход в матч против моего
же прошлого аплоада».

**Scope:**

`core/qa/corpus.py` — новый модуль:
- `CorpusEntry(path, audio_fingerprint, phash_frames, added_at)`.
- `Corpus` хранится в `~/.cache/yt_uniquifier/corpus/` как JSON + npz для
  pHash frame digests.
- `add(path)` — индексирует файл (запускает phash sample + chromaprint).
- `search_match(target, threshold) → list[CorpusEntry]` — для каждого entry
  в корпусе считает audio/visual similarity, возвращает те, что выше
  threshold.

`core/qa/cid_predict.py` — predictive scorer:
- Вход: пара (input_path, output_path) + опционально Corpus.
- Считает:
  - chromaprint Jaccard input ↔ output → нормирует к 0..1.
  - pHash distance в окне 4-сек блоков (не глобально) — Content ID работает
    chunk-by-chunk.
  - spectral centroid / rolloff distance через ffmpeg `astats` (proxy для
    spectral fingerprint shift).
- Возвращает `CIDPredictResult(match_probability_self, match_probability_corpus,
                                weakest_chunk)` — где weakest_chunk показывает
  4-сек блок с минимальным сдвигом (т.е. потенциальную точку матча).

`cli/cmd_corpus.py`:
- `yt-uniq corpus add <file>` — добавить в корпус.
- `yt-uniq corpus list` — показать.
- `yt-uniq corpus remove <file>`.

`cli/cmd_qa.py` — расширение:
- Флаг `--vs-corpus` — после обычного report'а проверяет output против
  всего корпуса, добавляет секцию в HTML/JSON.

`core/qa/report.py`:
- Новые поля в `QAReport`: `cid_predict_self`, `cid_predict_corpus`,
  `weakest_chunk_sec`, `chunk_similarities: list[float]`.
- HTML-шаблон: heatmap «similarity по 4-сек блокам» — видно, где output
  слишком похож на input.

**Acceptance:**
- Workflow: пользователь добавил свой старый upload в corpus →
  `yt-uniq run new_master.mp4 ...` → `qa.html` показывает CID-prediction
  против корпуса.
- На паре (identical file, same file) prediction_self ≈ 1.0.
- На паре (input, output после cid_aware профиля) prediction_self < 0.5.
- Heatmap корректно выделяет 4-сек блок с самым высоким сходством.

**Tests:**
- unit/test_corpus_add_lookup.py
- unit/test_cid_predict_thresholds.py с фикстурными метриками
- integration/test_qa_with_corpus.py: добавить в corpus tiny_clip,
  unique-обработать его, проверить что prediction_self < 1.0.

## Phase 9 — Calibration loop (own-content harness) (2 дня)

**Goal:** автоматизированная подстройка интенсивности трансформов под
конкретный исходник, чтобы выйти на целевой `match_probability`.

**Concept:** пользователь даёт исходник + старый upload (или просто
исходник для baseline self-match) + target probability (0.2 default). Tool
запускает итеративный bisect: грубая → точная конфигурация, останавливается
когда predicted match попадает в окно.

**Scope:**

`core/calibration/loop.py` — новый модуль:
- `CalibrationTarget(max_self_match: float = 0.2, min_vmaf: float = 88,
                     max_iterations: int = 5)`.
- `CalibrationStep(intensity_scale: float, profile_dump: dict, qa_result: ...)`.
- `calibrate(input, base_profile, target, work_dir) → CalibratedProfile`:
  - Шаг 1: запуск с base_profile, измеряем cid_predict + VMAF.
  - Шаг 2: если match > target → масштабируем `intensity_scale` ×1.5,
    повторяем. Если VMAF упал ниже min → откатываемся, уменьшаем шаг.
  - Bisection между «не сматчивается, но качество просело» и «качество
    хорошее, но матчится».
  - Возвращаем тюнингованный профиль + лог итераций.

`core/calibration/intensity.py` — функция масштабирования:
- `scale_profile(profile, factor)` — пропорционально увеличивает/уменьшает
  все «силы» (max_strength для crop_resize, strength для noise, |pitch-1|
  для pitch_tempo, и т.д.). Каждый transform определяет свой scale-метод.

`cli/cmd_calibrate.py`:
- `yt-uniq calibrate <input> --base profiles/cid_aware.yaml --out
                              tuned_profile.yaml [--target 0.2]
                              [--vs-corpus]`
- Выводит итоговый профиль + лог итераций + финальный QA-отчёт.

`core/profile_loader.py`:
- `dump_profile(profile, path)` — сериализация Profile → YAML.

**Acceptance:**
- На реальном клипе calibrate за 3–5 итераций выходит на target=0.2.
- Откалиброванный профиль можно использовать как обычный
  `yt-uniq run --profile tuned.yaml ...`.

**Tests:**
- unit/test_intensity_scaling.py: scale_profile(2.0) на medium даёт
  ожидаемые числовые сдвиги.
- unit/test_calibration_loop.py с mock'нутым `cid_predict` — проверяет
  логику bisect.
- integration/test_calibration_real.py: на tiny_clip, target=0.5,
  max_iterations=2 — заканчивается без exception.

## Phase 10 — Scale validation (1.5 дня)

**Goal:** убедиться что pipeline действительно работает на 2h+ файлах
без OOM, без зависаний, без визуальных регрессий, и время разумное.

**Scope:**

`tools/benchmark.py` — скрипт для одного-кнопочного прогона:
- Берёт реальный фильм (путь как аргумент).
- Запускает probe → preflight → run (medium профиль) → qa.
- Измеряет: peak RAM, total wall time, time per phase
  (keyframe scan, segments, audio pass, concat, qa).
- Пишет CSV отчёт.

`tools/seam_test.py` — проверка швов concat:
- Извлекает SSIM в окне ±2 кадра вокруг каждого segment-boundary в выходе.
- Сравнивает с SSIM в середине сегментов.
- Если разница > 0.005 — warning, выводит timestamp шва.

`core/segmenter.py` — оптимизации, если scale-тест покажет:
- Возможно — параллельная обработка сегментов на CPU (если encoder = libx264
  и нет GPU lock). Опция `--workers N`.
- Возможно — кеш `list_keyframes` по input_md5.

`core/qa/report.py`:
- Лимиты на samples=120 могут быть слишком жёсткими для длинного видео.
  Сделать `samples` пропорциональным длительности (например 30 кадров/мин,
  cap 600).

`core/qa/vmaf.py`:
- Опция `subsample` — VMAF только каждый N-й кадр для длинных файлов.

**Acceptance:**
- 2-часовой 1080p mp4 проходит на этой macOS:
  - Без OOM.
  - Wall time < 1.5× ffmpeg single-pass libx264 baseline.
  - Resume после kill восстанавливается корректно.
  - seam_test.py не находит видимых швов.
- QA отчёт строится за ≤ 10 мин (с VMAF) или ≤ 2 мин (без).

**Tests:** в основном manual/benchmark, не CI. Что попадает в CI:
- unit/test_segmenter_long_input_planning.py: mock-духи на 7200-секундный
  input, проверяем что plan_segments возвращает разумное количество
  сегментов (10–15 шт).

## Cross-cutting

### Метрики, которые мы хотим стабильно держать (после v0.2)

| Метрика | Target | Где измеряется |
|---|---|---|
| VMAF input↔output | ≥ 88 | qa report |
| pHash similarity input↔output | 0.6–0.85 | qa report |
| Chromaprint Jaccard input↔output | < 0.4 | qa report |
| CID predicted self-match | < 0.2 | cid_predict |
| HDR roundtrip VMAF | ≥ 90 | hdr integration test |
| Variability между двумя runs | chromaprint Jaccard < 0.7 | variability test |
| Wall time на 2h 1080p | ≤ 1.5× libx264 baseline | benchmark |

### Что НЕ входит в v0.2 (явно)

- **GUI / web UI / REST API / TUI.** Только CLI.
- HDR → SDR tonemap (отложено в v0.3).
- Image-based subtitles (pgs/dvb) — остаются «warning + skip».
- Параллельный GPU encoding (требует разбиения VRAM, не v0.2).
- Audio re-synthesis (TTS dub / voice cloning).
- Прямая интеграция с YouTube API для автоматической проверки match'а —
  заменено калибровкой против собственного корпуса.
- Bypass detection для произвольного третьего контента — вне scope.

### Риски

| Риск | Митигация |
|---|---|
| Variability ломает resume (разный run_seed → разный plan_hash → новый work_dir) | План: фиксировать seed в state.json при первом запуске, использовать его при resume; «новый вариант» = explicit `--new-variant` flag |
| Calibration loop долгий (каждая итерация — полный re-encode) | Калибровать на ПЕРВЫХ 60 секундах файла + extrapolate; финальный run на полном файле уже с найденным профилем |
| Spectral smear звучит неестественно на классической музыке/диалогах | Профиль `cid_aware` без spectral_smear как default; `cid_aggressive` только когда пользователь явно опт-инит |
| HDR через zscale теряет точность | Тестировать VMAF в HDR-режиме (`libvmaf=phone_model=0`); если просадка > 3 пункта — добавить опцию `keep_hdr_quality=high` (более тяжёлая обёртка) |
| Mirror меняет смысл (буквы в кадре зеркалятся) | По умолчанию `enabled: false` в `cid_aggressive`, пользователь включает явно для контента, где это допустимо |
| Корпус разрастается, lookup замедляется | Cap размера + LRU-eviction; индекс в одном npz файле, не in-memory dict |
| Calibration не сходится за max_iterations | Возвращаем «best so far» с warning'ом, не raise |

## Что делает v0.2 «идеальным» в смысле постановки задачи

После прохождения всех 5 фаз:

1. **Реальный HDR-мастер** проходит через pipeline без потери HDR.
2. **Каждый run даёт другой fingerprint** — можно загружать N вариантов
   серий / cut'ов одного фильма без collision между ними.
3. **Калибровка** под целевую `match_probability` автоматизирована —
   пользователь не угадывает, что включить в профиле.
4. **CID-prediction** в QA-отчёте показывает риск ещё до загрузки.
5. **Корпус собственных файлов** проверяется заранее — output гарантированно
   не сматчится против предыдущих загрузок.
6. **Валидировано на реальном фильме**, не только на 2-сек testsrc.

Это всё ещё не «безусловный обход Content ID» (такого не существует — CID
адаптивен и обучается на новых паттернах), но переходит из режима
